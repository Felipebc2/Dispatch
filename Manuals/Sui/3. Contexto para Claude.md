# Sui / Move — Context for Claude

Quick competition reference for **Sui** (blockchain) challenges written in **Move**. The model and
toolchain are quite different from EVM: there's no "contract with mutable global storage" —
everything is a typed **object** with an owner, and the logic is `public fun` in **modules**. A Sui
CTF almost always follows the same mold: you write a **`solve` module** that the launcher publishes
and calls, passing in the challenge's **shared objects**.

> ⚠️ The Sui toolchain may NOT be installed. Install on demand:
> - `suiup` (recommended): `cargo install --git https://github.com/MystenLabs/suiup suiup && suiup install sui`
> - or a direct binary from the MystenLabs/sui releases, or `brew install sui`.
> - Verify: `sui --version` · `sui move --help`.

## Move/Sui mental model (what changes the attack)

- **Objects, not storage:** state lives in `struct`s with `abilities` (`key`, `store`, `copy`, `drop`).
  An object with `key` has a `UID` and exists on-chain; a **shared object**
  (`transfer::share_object`) can be used by anyone (it's the typical target: `QuestBoard`, `Vault`,
  `Spellbook`, `Setup`).
- **Abilities govern what you can do:**
  - no `drop` → the value **must be consumed** (it can't be discarded) → the **hot-potato** pattern
    (e.g. a `Ticket` returned by `enter_tavern` that you're REQUIRED to pass to `checkout`, or it
    won't even compile). Understanding who creates and who consumes the hot-potato is key in many
    challenges.
  - no `copy` → you can't duplicate it; no `store` → you can't store it inside another object.
- **No classic msg.sender:** the caller comes from `TxContext` (`tx_context::sender(ctx)`).
  Permission is usually via ownership of an object (the capability pattern) or an address check.
- **No external-call reentrancy like EVM**, but there are equivalents: a **state machine** with a
  value-bearing function reachable from one extra state → a repeatable claim (see Arsenal).
- **Randomness:** `sui::random::Random` is a shared object; `#[allow(lint(public_random))]` appears
  when the solve uses random. The same EVM lesson applies: beware of predictable "random".

## Challenge template (OtterSec framework)

- `Setup`/the framework creates the objects and defines victory, like a `public fun isSolved(): bool`
  or a `prove(flag)` / getter that **reverts if not solved** (the flag comes out if it doesn't
  revert).
- You fill in a **`solve` module** with a fixed signature that receives the shared objects +
  `&mut TxContext`:
  ```move
  module solve::solve {
      use challenge::<mod>::{Self, <TYPES>};
      public fun solve(_board: &mut <Mod>::QuestBoard, _vault: &mut <Mod>::Vault<...>,
                       _player: &mut <Mod>::Player, _ctx: &mut TxContext) {
          // your call chain here
      }
  }
  ```
- **Launcher**: `nc host 31337`, a typical menu `1 launch / 2 kill / 3 flag`. You send the compiled
  `solve` module; the framework publishes it and calls `solve(...)` with the instance's objects,
  then checks the condition and hands over the flag.

## Solving flow

1. **Read the victory condition** (`isSolved`/`prove`/a getter) — the exact spec of the objective.
2. **Read the challenge module**: structs + abilities (look for a hot-potato = a struct with no
   `drop`), and the **state→function→state table** (which state each `public fun` enters, where it
   transitions to).
3. **Find the hole** (patterns already in the Arsenal):
   - validated index ≠ consumed element (`borrow(id)` vs `pop_back`) →
     `Arsenal/WEB/move-sui-validated-index-vs-consumed-element.md`
   - a claim function reachable from an extra state → repeatable reward →
     `Arsenal/WEB/move-sui-state-machine-reclaim-reward.md`
   - win = a puzzle in the source → supply the input that satisfies it →
     `Arsenal/WEB/move-sui-source-encoded-puzzle-input.md`
   - a "secret"/"private" input on-chain is not secret (read it from the Setup/storage).
4. **Build the chain** in `solve`, respecting abilities (consume hot-potatoes) and states.
5. Compile and submit; check victory; validate the flag.

## Sui CLI commands (reference)

```bash
sui move build                      # compile the Move package (looks for Move.toml)
sui move test                       # local Move tests
# publish / call (when you have direct chain access, outside the launcher):
sui client publish --gas-budget 100000000
sui client call --package <pkg> --module <mod> --function <fn> \
    --args <obj_ids...> --gas-budget 100000000
sui client object <id>              # inspect an object (on-chain state = public)
sui client objects                  # objects you own
```
In CTF the most common thing is just `sui move build` + sending the `solve` through the challenge's
client/launcher (not a manual `publish`). `Move.toml` needs to point the `challenge` dependency at
the challenge code.

## Gotchas

- **Doesn't compile = doesn't get sent:** ability errors (an unconsumed hot-potato, a value with no
  `drop` dropped) are blocked at the compiler. If you get stuck, it's almost always an object that
  needs to be passed along.
- **Shared objects come from the launcher** — you don't create them in `solve`, you just receive a
  `&mut` and operate on it.
- **`Move.toml` / versions:** match the Move edition and the `challenge` package dependency; the
  wrong `sui` version breaks the build. Use the same one as the handout if indicated.
- Objects are **typed and unforgeable**: you can't pass your own `QuestBoard` in place of the real
  one (it has a `UID` created by the contract). The vector is the logic, not faking the object.
- Validate against the CTF's configured flag format.
