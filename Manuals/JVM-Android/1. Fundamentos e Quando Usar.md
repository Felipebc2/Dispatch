# JVM-Android: Fundamentals and When to Use It

Introductory manual for reversing JVM bytecode (JARs, `.class`) and Android apps (APK, DEX),
including native methods via JNI. Walkthrough in `2. Guia Passo a Passo.md`; competition reference
in `3. Contexto para Claude.md`.

## What it is

Java and Kotlin compile to stack-based bytecode that decompiles back to near-source. That makes
these targets easy to read, so the difficulty is usually hidden somewhere off the obvious path: a
class decrypted and loaded at runtime, logic pushed into a native `.so`, or heavy obfuscation.

The kit by layer:
- **JARs / `.class`**: `javap -c -p` (raw bytecode), and decompilers CFR, Procyon, Fernflower.
- **APK**: `jadx` / `jadx-gui` (DEX to Java in one step), `apktool d` (smali plus resources),
  `unzip` then `dex2jar` to get a JAR for the Java decompilers.
- **Native**: JNI methods live in `lib/<abi>/*.so`; reverse those in Ghidra (see its manual).
- **Dynamic**: `jdb` for JVM, Frida to hook methods on a running app or process.

## When it is the right tool

- A `.jar`, `.class`, `.apk`, or a bare `classes.dex`.
- A Java front end that looks like a decoy, with a hint that the real check runs elsewhere (a
  custom `ClassLoader`, a `System.loadLibrary`, a native method).
- You need bytecode-level truth because a decompiler produced something that will not recompile.

## When it is NOT

- The app is a thin wrapper over a web API: the logic is server-side, treat it as WEB.
- The target is a standalone native ELF with no JVM involved: that is plain Ghidra REV.

See `3. Contexto para Claude.md` for the decision flow and paste-ready commands.
