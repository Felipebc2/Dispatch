# TON: Context for Claude

Quick competition reference for **TON** (The Open Network) challenges: a non-EVM chain, contracts
in **Tolk/FunC**, an economy of **jettons** (TON tokens). The toolchain is the **TON SDK**
(Node/Python), **not** Foundry/cast. The mental model is quite different from EVM: everything is an
**asynchronous message** between contracts, each with its own storage; there's no "synchronous call
that returns" like in Solidity.

> ⚠️ The TON toolchain may NOT be installed on this machine. Install on demand:
> - Node: `npm i @ton/ton @ton/crypto @ton/core` (versions seen in competition: `@ton/ton >=16.2.2 <17`,
>   `@ton/crypto ^3.3.0`, `@ton/core ~0`).
> - Python (alternative): `pip install pytoniq` (an ADNL/liteserver client) or `tonsdk`.

## Model differences that change the attack

- **Asynchronous by messages:** one action = sending an internal message to a contract; the
  response comes in ANOTHER message/transaction. You can't "read the return and react in the same
  tx" like with an EVM attacker contract. Chaining is by a sequence of messages, not by classic
  reentrancy.
- **No global, value-trustworthy msg.sender:** handlers check `transferInitiator`, `senderAddress`,
  `in.valueCoins`. A common vector: the handler validates **who initiated** it but not **where the
  value came from**.
- **Jettons:** the token standard = a JettonMinter (issues) + a JettonWallet per owner.
  Transferring a jetton = sending a `0x0f8a7ea5` (ask-to-transfer) message to your JettonWallet,
  which notifies the recipient with a `forwardPayload` (the challenge action's "opcode" goes in the
  payload).
- **The player's wallet:** a version like `v3r2`, identified by `walletId` + `seed` (32 bytes hex).
  The launcher hands you this data; you sign txs with the seed.

## TON launcher (instancer) pattern

A recurring format:

- A **TLS connection via `nc`** on a port (e.g. 1337). Menu: `new` (creates an instance), `flag`
  (asks for the flag if `isSolved()`), `kill`.
- There's often a **Proof-of-Work** before creating an instance: the server sends a `prefix` +
  `difficulty`; you find a `suffix` such that `sha256(prefix+suffix)` starts with `difficulty` hex
  zeros.
- `new` returns: `uuid`, `challenge contract address`, `api v2` (`https://.../instance/<uuid>/api/v2`),
  `wallet version`, `wallet id`, `seed`.
- `flag` + `uuid` → the server checks `isSolved()` on-chain (a getter) and returns the flag only if
  `true`.

A generic PoW solver (stdlib):
```python
import hashlib, itertools, string
def solve_pow(prefix, difficulty, alphabet=string.ascii_letters+string.digits):
    for n in range(1, 12):
        for c in itertools.product(alphabet, repeat=n):
            s = ''.join(c)
            if hashlib.sha256((prefix+s).encode()).hexdigest().startswith('0'*difficulty):
                return s
```

## Solving flow

1. **Read the victory getter** (`isSolved()`) and the solve handler(s) in the `.tolk`/`.func`:
   just like EVM, the solve is the exact spec of the objective.
2. **Map the opcodes/messages** (`messages.tolk`): each challenge action is an opcode in the message
   body or in the `forwardPayload`. E.g.: `PlayerBonus 0x13370002`, `Buy 0x13370003`,
   `Sell 0x13370004`, `Solve 0x13370005`, jetton transfer `0x0f8a7ea5`.
3. **Map the economy / gates**: how much each action costs/yields, what's "one-time-only"
   (`remainingPlayerBonus`), value limits (`assert in.valueCoins > ...`).
4. **Check isolation between instances** (see below): a recurring bug in TON launchers.
5. **Build the message sequence** in Node (`@ton/ton`): open the wallet from the seed, send messages
   with a `forwardPayload` carrying the opcode, wait for confirmation between steps (asynchronous).
6. Confirm `isSolved()` → ask the launcher for the flag with the `uuid`.

## Solver skeleton (Node, @ton/ton)

```js
import { TonClient, WalletContractV3R2, internal, Cell, beginCell, Address } from '@ton/ton';
import { mnemonicToPrivateKey } from '@ton/crypto';
// instance's api v2: new TonClient({ endpoint: '<api v2>' })
// wallet: WalletContractV3R2.create({ workchain:0, publicKey, walletId })
// seed hex -> keyPair; open via client.open(wallet)
// send: await walletContract.sendTransfer({ secretKey, seqno, messages:[ internal({ to, value, body }) ] })
// action body = beginCell().storeUint(OP, 32)....endCell()  (OP = the challenge's opcode)
// jetton transfer: 0x0f8a7ea5 message to your JettonWallet, with forwardPayload = the challenge opcode
```

In competition, the fastest thing is usually to **adapt a ready-made solver** (many TON writeups
ship one) rather than write from scratch: the cell/jetton assembly is verbose.

## Recurring attack insight: cross-instance isolation

The launcher gives an API scoped by UUID, but the wallets/contracts of different instances live in
the **same local TON world**. A "donor" instance can fund the wallet of another "target" one. If
the solve handler only validates the initiator (not the origin of the value), an economic gate
"impossible on one instance" becomes trivial with two. See
`Arsenal/WEB/web3-cross-instance-shared-state-economic-gate.md`.

## Gotchas

- **Asynchronous:** wait for each message to confirm (check seqno / balance / jettons) before the
  next; sending everything at once breaks the order.
- **Gas in TON:** almost every message needs TON for gas/forward (e.g. `BUY_MINT_TON_AMOUNT 0.12`).
  Underestimating the value → `INSUFFICIENT_FUNDS` or the message gets swallowed.
- **TON addresses** have forms (raw `0:...` vs. friendly `EQ.../UQ...`); use the one the
  SDK/endpoint expects. `Address.parse()` normalizes.
- Validate against the CTF's configured flag format.
