# WebAssembly: Fundamentals and When to Use It

Introductory manual for reversing a WebAssembly (`.wasm`) module with the wabt toolkit. Practical
walkthrough in `2. Guia Passo a Passo.md`; competition reference in `3. Contexto para Claude.md`.

## What it is

WebAssembly is a stack-based bytecode that runs in browsers and in standalone runtimes (wasmtime,
node). A `.wasm` file is a compact binary with typed functions, a linear memory, and explicit
imports and exports. In CTFs it shows up as a client-side check ("the flag validator runs in your
browser") or as a standalone binary you must read or drive.

The wabt (WebAssembly Binary Toolkit) suite is the core kit:
- `wasm-objdump`: headers, sections, imports, exports, the function and data tables.
- `wasm2wat`: lift the binary to WAT, the readable text format.
- `wasm-decompile`: a C-like view, usually the fastest way to grasp the logic.
- `wasm2c`: emit C you can compile and run or instrument.
- `wasm-validate`: confirm the module is well formed.

## When it is the right tool

- The challenge ships a `.wasm`, or a web page loads one via `WebAssembly.instantiate`.
- A JavaScript front end is thin and the real work (a keygen, a checker, a decoder) is in the
  module.
- You need to read the embedded data segment (strings, expected bytes, tables) or call an export
  with candidate input to see what it returns.

## When it is NOT

- The logic is actually in the JavaScript glue (common with Emscripten); read the `.js` first.
- The module is a generic runtime and the interesting data is server-side.
- You only need to find a static string: `strings`/`wasm-objdump -x` may be enough without a full
  lift.

See `3. Contexto para Claude.md` for the decision flow and the paste-ready commands.
