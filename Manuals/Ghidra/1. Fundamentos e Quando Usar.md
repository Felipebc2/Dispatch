# Ghidra: Fundamentals and When to Use It

Introductory manual: what Ghidra is, the concepts you need to grasp before opening a binary, and
the situations where it's worth using (with or without AI). For the practical usage walkthrough,
see `2. Guia Passo a Passo.md`.

## What Ghidra is

Ghidra is an open-source software reverse-engineering framework maintained by the NSA. It takes a
compiled binary (executable, library, firmware) and reconstructs a readable view of what the code
does, without needing the original source code.

Two main views of the same code:

- **Disassembly (Listing):** the binary translated to assembly (CPU instructions: `mov`, `call`,
  `jmp`, etc.). Faithful to what the CPU executes, but verbose and slow to read.
- **Decompilation (Decompiler):** Ghidra tries to reconstruct something close to C code from the
  assembly, a "pseudo-C". It doesn't compile back, but it's far faster to understand than raw
  assembly. This is the view you'll use most.

## Key concepts

- **Project vs. Program:** a Ghidra *project* is a working folder (it can hold several binaries). A
  *program* is a specific binary imported into the project.
- **Auto-analysis:** when you import a binary, Ghidra runs a battery of analyzers that identify
  functions, strings, cross-references, data types, etc. Without it, you just have raw bytes.
- **Function:** a block of code identified by the analyzer (or by you, manually). Each function has
  an address, a (editable) name, and, if decompiled, a signature (return type + parameters).
- **Symbol/Label:** a name given to an address (function, global variable, string, jump label). By
  default Ghidra uses generic names (`FUN_00401230`, `DAT_00402000`) until you (or the AI) rename
  them with something meaningful.
- **Cross-reference (xref):** the "who calls whom" / "who reads or writes this address" relation.
  The basis of any investigation: starting from a suspicious string or variable, the xrefs lead to
  the function responsible.

## What GhidraMCP is

GhidraMCP is a bridge (MCP, Model Context Protocol) between Ghidra and an AI agent like Claude.
Instead of clicking into each function and reading the decompilation yourself, you converse:
"decompile this function and explain it", "where is this flag validated?", "rename these
variables". Ghidra exposes 253 tools via MCP, from listing functions and decompiling to creating
structs, emulating code, and running scripts.

## When Ghidra is worth using

- **CTF, Reverse (REV) category:** understanding a flag-validation algorithm, a custom cipher, a
  serial/keygen. This is the most common use case in competition.
- **CTF, Pwn/Binary category:** before writing an exploit (buffer overflow, format string, heap),
  you need to understand the binary's structure: vulnerable functions, active protections
  (canary, NX, PIE), execution flow.
- **Malware analysis:** identify behavior (persistence, C2, exfiltration), extract IOCs
  (IPs, domains, mutexes), detect anti-analysis techniques.
- **Closed-binary auditing:** find a vulnerability or understand proprietary logic without having
  the source code.
- **Version comparison (patch diffing):** what changed between two builds of the same binary,
  useful for understanding what a security patch fixed.

## When it's NOT worth it

- **Trivial encoding challenges** (base64, hex, rot13): it's not even reverse engineering; solve
  it in seconds with CyberChef or by hand.
- **Pure crypto with no binary** (misconfigured RSA, a classical cipher): there's nothing to
  reverse, the challenge is in the math, not the binary.
- **When you already recognize the pattern off the top of your head**: if you open the challenge
  and already know what it is, opening Ghidra and waiting for the analysis to run is slower than
  solving it directly.

This same logic applies to deciding between using AI or doing it manually; see the
`[[6. Quando Não Usar IA]]` note from the CTF workshop.

## Ghidra alone vs. Ghidra + Claude (MCP)

| Situation | Best approach |
|---|---|
| Small binary, obvious function, you already know assembly/C | Ghidra alone, faster than describing context to the AI |
| Large binary, many functions, you need to quickly map what's relevant | Claude + MCP: lists/filters functions, points out candidates, you focus only on those |
| A 200+ line decompilation with confusing logic | Claude + MCP: it reads and summarizes in seconds |
| Renaming/typing dozens of variables to make the code readable | Claude + MCP: batch renaming, you just validate |
| You already know exactly what to look for (e.g. "the flag comparison chain") | Either one, but MCP saves clicks (string search → xref → decompile in one request) |
