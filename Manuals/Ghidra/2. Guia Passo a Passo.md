# Ghidra: Step-by-Step Guide

A complete workflow, from zero, for anyone who has never opened Ghidra: from the environment check
to solving a binary by conversing with Claude via GhidraMCP. Concepts and "when to use" are in
`1. Fundamentos e Quando Usar.md`: this manual is just the walkthrough.

## 0. Quick environment check

```bash
# Ghidra installed?
ghidra --version 2>&1 || echo "not found"

# GhidraMCP running? (Ghidra must be open)
curl http://127.0.0.1:8089/check_connection
```

Expected response when no binary is open yet: `Connected: GhidraMCP plugin running, but no
program loaded`. If you get "Connection refused", open Ghidra first (step 1).

## 1. Open Ghidra and create a project

```bash
/opt/ghidra/ghidraRun
```

In the **Ghidra Project Window** (the first one that opens):

1. `File > New Project`
2. Choose **Non-Shared Project** (a local project, no server) → Next
3. Give it a name (e.g. `ctf-project`) and choose a folder to store the project → Finish

You don't need to create a new project for every binary: a project can hold several programs.
One project per CTF/event is enough.

## 2. Import a binary

1. `File > Import File`
2. Select the challenge file (ELF, PE, etc.)
3. Ghidra detects the format and architecture automatically; when in doubt, accept the suggested
   values and click **OK**
4. The file appears in the project list. **Double-click** it to open it

## 3. Auto-analysis

When you open it for the first time, Ghidra asks **"Analyze now?"**: click **Yes** and accept the
default options in the next dialog (**Analyze**).

This runs the analyzers that identify functions, strings, references, data types, etc. Without this
step the binary is just a sequence of bytes with no structure. Time: from seconds to a few minutes,
depending on the binary's size.

## 4. Quick tour of the interface (CodeBrowser)

After analysis, you're in the **CodeBrowser** window. The areas that matter:

| Panel | Where it is | What it's for |
|---|---|---|
| **Listing** | Center | Assembly, address by address, the "raw" view |
| **Decompiler** | Right (or `Window > Decompiler`) | Pseudo-C of the function selected in the Listing, your main view |
| **Symbol Tree** | Left | List of functions, labels, namespaces, imports/exports |
| **Data Type Manager** | Left (tab) | Structs, enums, defined types |
| **Console** | Bottom | Log of scripts and errors |

Basic flow: click a function in the **Symbol Tree** → the **Listing** jumps to it → the
**Decompiler** shows the corresponding pseudo-C side by side.

## 5. Essential manual actions

- **Search strings:** `Search > For Strings` lists all readable text in the binary. Strings like
  `"Wrong password"`, `"flag{"`, or function names point straight to the relevant code.
- **Go to an address/symbol:** `G` (shortcut) or `Navigation > Go To`
- **Rename a function/variable:** right-click the name (in the Listing or Decompiler) → `Rename`
- **See who calls/uses something (xref):** right-click → `References > Show References to Address`
- **Comment:** right-click → `Comment > ...` (Plate = above the function, EOL = end of line)
- **Bookmark:** `Ctrl+D` on an important address, to find it quickly later in `Window > Bookmarks`
- **Save:** `File > Save` (or `Ctrl+S`) saves annotations/renamings to the project

## 6. Workflow with Claude Code (GhidraMCP)

With the binary open and the extension active, open a Claude Code session **inside the folder where
the `ghidra` MCP is registered** (see the `[[Ghidra MCP]]` note, the server is registered in a
scope local to that directory) and converse normally. Some useful requests and the MCP tool that
kicks in behind the scenes:

| You ask | MCP tool used |
|---|---|
| "list this binary's functions" | `list_functions` / `list_functions_enhanced` |
| "what suspicious strings are here?" | `search_strings` / `list_strings` |
| "decompile the `main` function and explain it" | `decompile_function` |
| "who calls this function?" / "what does it call?" | `get_function_callers` / `get_function_callees` |
| "rename this function to `validate_password`" | `rename_function` |
| "rename these variables with names that make sense" | `rename_variables` / `set_variables` |
| "comment this function explaining what it does" | `set_comment` |
| "what does this struct look like?" | `get_struct_layout` |
| "where else is this string/address referenced?" | `get_xrefs_to` / `get_xrefs_from` |
| "run the function in isolation with this input" (P-code emulation) | via `analyze_dataflow` / emulation tools |

You stay in control: the AI reads, explains, and suggests; you decide what to accept, rename, or
keep investigating.

## 7. Practical routine (your first CTF binary)

A sequence that works for most REV challenges:

1. **Entry point:** find `main` (or `entry`) in the Symbol Tree
2. **Suspicious strings:** `Search > For Strings` to look for error/success messages
   (`"Correct!"`, `"Wrong"`, `"flag{"`)
3. **Xref the string:** right-click the string → `References > Show References to Address`, which takes
   you straight to the function that uses it
4. **Decompile that function:** look at the pseudo-C (or ask Claude to decompile and explain)
5. **Follow the logic backward:** who calls this function? What data does it receive?
   (`get_function_callers`)
6. **Rename as you understand:** keep making the code readable as you go
7. **Find the flag comparison/condition:** usually it's an `if (strcmp(...) == 0)` or a
   byte-by-byte validation loop; reconstruct the logic (sometimes you can invert it by hand,
   sometimes you need to run the binary)

## 8. Wrapping up

- `File > Save` in the CodeBrowser before closing; this keeps renamings and comments
- The project stays saved in the folder you chose in step 1, so you can reopen and continue later
- If you're going to open another binary from the same event, repeat step 2 within the same project
