# chrome-devtools (MCP) — Context for Claude

Quick competition reference. Controls a **live Chrome/Chromium** via MCP (prefix
`mcp__chrome-devtools__*`), with the full power of DevTools: DOM, console, network, JS,
performance. Registered in a scope local to this project (see `claude mcp get chrome-devtools`).
The tools come online at the next session start.

> Current setup: points at `/usr/bin/chromium`, `--isolated` (temporary profile). If you need to
> attach to an already-open Chrome (e.g. a logged-in session), reconfigure with
> `-u http://127.0.0.1:9222`.

## When to use (client-side WEB)

When the challenge logic/flag lives **in the browser**, not on the server:

```
Heavy frontend JS / SPA (React/Vue) / obfuscated app
  → read/run the JS in the page context instead of reconstructing it by hand

Flag/secret hidden in the client
  → in a global JS variable, localStorage/sessionStorage, IndexedDB, a cookie, a DOM comment

A flow that only happens through interaction (login, multi-step, modal, canvas)
  → automate the click/fill and observe the effect

An API/websocket call fired by the frontend
  → capture it in the network panel (endpoint, headers, token, body) to attack it directly later

DOM-XSS / a client-side sink
  → inspect sinks, test a payload, and watch it execute in the console
```

If the attack is 100% server-side (SQLi, SSRF, path traversal via `curl`), **you don't need the
browser** — `curl`/`sqlmap` solve it faster. chrome-devtools is for what `curl` can't see
(JS/DOM/client state).

## Main tools (mcp__chrome-devtools__*)

| Goal | Tool |
|---|---|
| Open URL / new tab / list tabs | `navigate_page`, `new_page`, `list_pages` |
| See the page (visually) | `take_screenshot` |
| See the actionable structure/DOM (a11y tree with uids) | `take_snapshot` |
| Interact | `click`, `fill`, `fill_form`, `hover`, `drag`, `upload_file` |
| **Run JS in the page context** | `evaluate_script` ← the most useful for reading client state |
| Network: list / detail a request | `list_network_requests`, `get_network_request` |
| Console (errors, logs, stack map) | `list_console_messages` |
| Wait for a condition | `wait_for` |
| Performance (trace/insights) | `performance_start_trace`, `performance_stop_trace` |

## Competition recipes (via `evaluate_script`)

Read client secrets without reconstructing the JS:

```js
// entire localStorage + sessionStorage
() => ({ local: {...localStorage}, session: {...sessionStorage}, cookie: document.cookie })

// sweep suspicious globals (flag, token, key, secret)
() => Object.keys(window).filter(k => /flag|token|key|secret|admin/i.test(k)).map(k => [k, window[k]])

// dump IndexedDB (database names)
async () => (await indexedDB.databases()).map(d => d.name)

// find flag-like strings in the whole rendered HTML
() => (document.documentElement.innerHTML.match(/flag\{[^}]+\}/gi) || [])
```

Capture the real endpoint the frontend calls → then attack it with `curl`/a solver:
`navigate_page` to the page → trigger the action (`click`) → `list_network_requests` →
`get_network_request` to grab the URL/headers/token/body.

## Typical flow

1. `navigate_page` to the challenge URL.
2. `take_snapshot` to map the actionable DOM (grabs the elements' `uid`s).
3. `evaluate_script` to read client state (storage/globals/DOM) — often the flag is already here.
4. If interaction is needed: `click`/`fill` guided by the snapshot's uids, then re-evaluate.
5. `list_network_requests` to extract a hidden API/token and, if the attack continues server-side,
   pass the endpoint to `curl`/a solver.
6. Validate against the CTF's configured flag format.

## Gotchas

- `--isolated` starts with no session/login — if the challenge requires being logged into a
  profile, reconfigure the MCP (`-u` for a Chrome with debugging, or a persistent `--userDataDir`).
- Chromium ≠ official Chrome: most tools work, but edge-case features may vary.
- Headless (`--headless`) is faster on a server, but some challenges detect headless —
  if the behavior changes, run with the UI.
